# Chirp MVP v2 设计：军师 agent + 情侣客厅 + 日记本（三角色架构）

日期：2026-07-12
状态：已与 Rae 对齐（本文档为定稿评审版）
来源：飞书 wiki「New version / MVP」章节（doc KCNjdo5IsoP41GxgcTpcHqmFn0c）+ 2026-07-12 设计对话
关系：**取代** `2026-07-03-couples-p0-design.md` 的产品层设计；其数据层/基建层设计（邀请钥匙、RLS membership 改造、Realtime、消息双列约定）继续有效，本文引用不重复。

## 1. 定位

**一句话定位：你们关系的第三个成员 + 各自的军师。** 平时各自的 agent 陪伴你、帮你记住重要的事；有话要正式说给对方听的时候，去你们的客厅（群聊）；吵架了，Bird 帮你们把话说开。

- 结构 = 高频养低频：军师 DM（高频陪伴）→ 日记本（资产沉淀）→ 调解（低频高光，也是差异化和口碑点）。
- 获客滩头：异地恋情侣（对共同数字空间需求最强、小红书触达成本最低）。仅为获客锚点，不约束产品结构。
- 获客漏斗：单人先用军师（完整单人价值）→ 军师在合适时机建议邀请对象 → 对方进来后解锁客厅和共同日记。

## 2. 角色与记忆边界

三个角色，**agent 身份 = 记忆边界**，无任何跨房间裁剪/搬运规则，无人需要"装不知道"：

| 角色 | 是什么 | 可见范围 |
|---|---|---|
| A 的私人 agent | A 的军师/朋友（**不是 A 的分身**，永远以自己的身份说话） | A 的 DM + 群聊 + 我们的故事 + A 的「我的日记」+ A 的 about me |
| B 的私人 agent | 同上，对称 | B 侧同上 |
| Bird | 情侣共同拥有的调解员/客厅主人 | 群聊 + 我们的故事 + 调解提交（仅调解流程内，明示） |

出发点式规则：

- **agent 的可见范围 ≤ 它主人的可见范围**——因为 agent 知道的都是主人本来就看得到的东西，所以它在任何场合说话都不可能泄露对方的隐私，隔离由架构保证而非 prompt 约束。
- **Bird 没有 DM**——因为私人陪伴/树洞已由私人 agent 承担，第二个私聊入口徒增困惑；Bird 只活在共同场合，"全局记忆但群里不说"的行为泄露问题从根上不存在。
- **私人 agent 永远不与对方单独相处**——因为它满载主人隐私，单独面对对方即存在被套话的侧信道。派遣功能（后面做）也必须在双方都在场的群里进行。
- **军师价值观护栏**——军师忠于主人，但北极星是"主人的幸福（含这段关系的健康）"：不教唆操纵、不拱火、不代替主人做判断。写入军师 system prompt。

## 3. 模块与 MVP 范围

### 模块 1：agent 陪伴/军师（MVP）

- 每人一个私人 agent，DM 形态，复用现有 persona 链路（instance/记忆/DM），换军师 prompt + 价值观护栏。
- 开屏 onboarding：几个快问题（可 skip），答案落入 about me 个人信息区，供军师冷启动。
- **主动日期记忆**：军师在对话中听到重要日期（生日/纪念日/相识日）→ 问一句"要我记住这个日子吗？"→ 写入结构化重要日期表；提醒功能只读这张表。个人日期归个人，关系日期（纪念日等）双方共享、Bird 可读。
- 主动提醒：基于重要日期表做纪念日/生日提醒。
- 派遣（代主人去群里向对方说话）：**后面做**；做时以"军师/朋友"身份带着主人确认过的内容进群，纯传话、不应答、说完退场。

### 模块 2：群聊 = 客厅（MVP）

- 定位：**有话正式说给对方听的地方**，不与微信抢日常斗嘴。一对情侣一个群（沿用一 planet 一群）。
- Bird @才响应（含引用），不 @ 保持安静；Bird 知道全部群聊上下文。
- **冷启动 = 四个轻入口**（输入框上方）：帮我们看看 / 一起做个决定 / 有件事想说清楚 / 矛盾调解。点击后 Bird 接管开场。
- 调解两模式，Bird 开场问"你们想在这里一起聊，还是先分别跟我说完，我再帮你们整理？"：
  - **直接说（MVP）**：就地在群里进行，Bird 中立、帮双方把话说清楚、分析问题给建议。
  - **分开说（切片 2）**：**表单式私密提交**，不是对话——群里出现调解卡片 → 各自点进去回答 Bird 的几个引导问题（仅本人可见）→ 卡片显示提交进度（1/2）→ 双方都提交后 Bird 合成共享议程发进群。出发点：表单没有流式/多轮状态机，成本低一个量级，且"提交"语义本就比"聊天"贴合；私密提交内容属"明示交给调解员"，是 Bird 唯一触碰个人侧内容的通道。

### 模块 3：日记本（MVP，纯文本）

- 两本写死：「我的日记」（私有：本人 + 本人 agent 可见）+「我们的故事」（共享：双方 + 双方 agent + Bird 可见）。"新建多主题日记本"后面做。
- 「我们的故事」分区：人写的 / agent 写的，agent 条目署名是谁的 agent。
- **agent 写共享区每条须经主人确认后发布**——因为 agent 知道主人的私密内容，写入共享空间等于搬运，必须有主人这道闸。写「我的日记」不需确认。
- 多模态（图片等）：后面做（依赖图片消息基建，另立项）。
- AI 引导/comment、轻量标记（Moment/promise/plan/unfinished）：后面做，观察后定。

### 模块 4：about me（MVP 仅做个人信息页壳）

- MVP：个人信息页 = onboarding 答案 + 重要日期 + **邀请入口（常驻于此）**。
- 恋爱人格测试、Insight from bird、月度总结信件、Relationship Changelog、第一封信：后面做（与记忆系统一起，边服务第一批用户边 build）。

## 4. 单人期与邀请

- B 未加入时：A 只有军师 DM（+日记本个人本）可用；**群聊在邀请被接受后才创建**（Bird @才响应，单人群没有意义）。
- 邀请：沿用 07-03 spec 的钥匙机制（`chirp_invites`、redeem 幂等、错误文案）；入口常驻 about me，军师可在合适时机建议发起。
- B redeem 后：走同一开屏 onboarding，获得自己的军师，进入客厅；历史群消息对 B 可见（成员可读整个会话）。

## 5. 数据层增量（相对 07-03 spec）

- 沿用：`chirp_invites`、RLS owner→membership 改造、Realtime 订阅、消息双列约定、visibleRunLock。
- 移除：bird_dm 会话不再创建（旧表/链路保留，入口下线）；memoryScope 的跨房间裁剪规则简化为"按 agent 身份取各自会话范围"。
- 新增：
  - 重要日期表（user_id、label、date、lunar 标记、scope=personal/couple）。
  - 日记表（book：my/ours；entry：author_type=human/agent、author_id、经确认标记）。
  - 调解会话表（切片 2）：状态机 pending_submissions → agenda_posted；私密提交内容仅 service role 可读。
- ⚠️ 记忆架构既有定论（"Bird 拥有全量全局记忆"）**在本设计中反转**：Bird 只持有共享层。实施前重过 memory 决策链与 distiller 现状。

## 7. 非目标（MVP 明确不做）

派遣、persona 社区、agent 进微信、恋爱人格测试、月度信件/第一封信/Changelog、多主题日记本、多模态、语音输入、AI 日记引导、每日一问（被四入口方案替代）、旧多 persona 星球功能恢复（继续隐藏不删）。

## 8. 观察清单（"先做框架看行为"要观察什么）

- 四个入口哪个被点：验证客厅的真实用途排序（调解 vs 决策 vs 表达）。
- 军师 DM 聊什么：需求信号的主矿区（用户向军师抱怨/求助什么 = 下一个功能）。
- 群聊沉默程度：预期稀疏，不视为失败信号；若两周零消息，考虑恢复每日一问类心跳。
- 邀请转化：发起数 / redeem 数 / B 次日留存。
- 日记：人写 vs agent 写的比例、确认闸的通过率。

## 9. 遗留与风险

- RLS 回归、`chirp_planet_members` 线上结构核对：沿用 07-03 spec §10。
- 军师 vs ChatGPT 差异化成立前提：长期关系记忆 + 与客厅/调解联动 + 形象。若第一批用户把军师当通用聊天机器人用后流失，优先补记忆深度而非功能。
- Bird 调解质量冷启动：Bird 只见过群聊，首次调解无积累。缓解：调解开场引导 + 分开说提交本身就是信息收集。
- 军师主动性（提醒/建议邀请）的打扰边界需真实调参，属可调项。
